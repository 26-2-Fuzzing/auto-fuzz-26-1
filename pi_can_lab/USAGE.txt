Raspberry Pi B/I/P/C-CAN 실험 도구 사용법
==========================================

0. 구성과 파일 역할
-------------------

이 폴더는 송신과 수신을 별도 프로세스로 실행하도록 구성되어 있습니다.

  can_receiver.py             모든 raw CAN 프레임 저장 + 선택 신호 DBC 해석
  can_sender.py               raw frame 또는 DBC 신호 변경 frame 송신
  dbc_lookup.py               다른 ID/신호를 찾을 때 사용하는 DBC 검색기
  self_test.py                CAN 장비 없이 설치 및 DBC encode/decode 검사
  receiver_b_can.yaml         B-CAN Pi 수신 설정
  receiver_i_can.yaml         I-CAN Pi 수신 설정
  receiver_p_can.yaml         P-CAN Pi 수신 설정
  receiver_c_can.yaml         C-CAN Pi 수신 설정
  sender_hazard_button.yaml   0x65A Hazard 버튼 후보 송신 설정
  sender_hazard_status.yaml   0x366 Hazard 상태 후보 송신 설정
  sender_hazard_mutation.yaml 상위 Mutator 기반 0x366 mutation 설정
  analyze_fuzz_response.py    TX manifest와 I/P-CAN 로그 상관분석
  FUZZ_ANALYSIS.md            회차별 로그/보고서와 유의미한 결과 판정 기준
  DBC_ANALYSIS.txt            제공된 DBC의 Hazard 관련 분석

같은 can_receiver.py를 각 수신 장비에서 실행하며 YAML만 다르게 사용합니다.
B-CAN Pi에서는 수신기를 터미널 1에서 계속 실행하고, 송신기를 터미널 2에서 실행합니다.


빠른 실행 순서
--------------

아래 명령은 모두 저장소 루트(auto-fuzz-26-1)에서 실행합니다. 먼저 각 장비의 시간을
NTP/chrony로 동기화하고 I-CAN/P-CAN 수신기를 시작합니다.

  # I-CAN 장비
  python3 pi_can_lab/can_receiver.py --config pi_can_lab/receiver_i_can.yaml

  # P-CAN 장비
  python3 pi_can_lab/can_receiver.py --config pi_can_lab/receiver_p_can.yaml

B-CAN 장비에서는 can0 상태와 0x366 수신 여부를 확인한 뒤 mutation preview를 실행합니다.
preview에는 실제 CAN 송신이 없습니다. live base는 같은 0x366 payload가 연속 3회 잡혀야
확정되므로, 5초 안에 조건을 만족하지 못하면 송신하지 않고 종료합니다. candump는 0x366이
반복 수신되는 것을 확인한 뒤 Ctrl+C로 끝냅니다.

  ip -details -statistics link show can0
  candump can0,366:7FF
  python3 pi_can_lab/can_sender.py \
    --config pi_can_lab/sender_hazard_mutation.yaml --count 16

preview의 ID, BASE, 자동 생성 seed, mutation 수와 payload를 검토한 후
격리된 벤치에서만 실행합니다.

  python3 pi_can_lab/can_sender.py \
    --config pi_can_lab/sender_hazard_mutation.yaml --execute

송신 종료 후에도 I-CAN/P-CAN 수신을 10초 이상 유지하고 Ctrl+C로 종료합니다. 각 장비의
pi_can_lab/logs/*.jsonl을 분석 PC의 같은 경로로 모은 다음 반응 보고서를 생성합니다.

  python3 pi_can_lab/analyze_fuzz_response.py \
    --tx pi_can_lab/logs/b_can_hazard_mutation_tx.jsonl \
    --rx i_can=pi_can_lab/logs/i_can.jsonl \
    --rx p_can=pi_can_lab/logs/p_can.jsonl \
    --dbc A5.dbc \
    --output pi_can_lab/logs/hazard_response.json

상세 설정, 안전 제한, 결과 해석은 아래 절을 따릅니다.


1. 반드시 먼저 확인할 사항
--------------------------

이 코드는 허가된 시험 차량 또는 격리된 벤치에서만 사용합니다.
실제 주행 중에는 송신하지 마십시오. 전류 제한 전원과 즉시 차단 수단을 준비하십시오.

제공된 파일은 파일명과 내용상 I-CAN K-Matrix입니다. 따라서 0x65A/0x366이 B-CAN에
실제로 존재한다고 단정할 수 없습니다. 처음에는 송신하지 말고 세 버스에서 수신한 뒤,
차량의 Hazard 스위치를 직접 눌러 어느 버스에서 어떤 신호가 변하는지 확인하십시오.

CAN-H/CAN-L/GND를 확인하고, 기존 차량 버스에 연결할 때 임의로 120옴 종단저항을
추가하지 마십시오. 실험 장치만 구성한 벤치라면 양 끝 종단 구성을 별도로 확인하십시오.


2. Raspberry Pi 준비
--------------------

각 장비에는 저장소 전체를 같은 경로에 복사하는 방법을 권장합니다. YAML은 저장소 루트의
A5.dbc를 사용하고 mutation 송신기는 상위 src/mutation/mutator.py를 직접 불러오므로
pi_can_lab 폴더만 따로 복사하면 안 됩니다.

각 Pi에서 저장소 루트로 이동한 후 다음을 실행합니다.

  sudo apt update
  sudo apt install -y python3-venv can-utils
  python3 -m venv .venv
  source .venv/bin/activate
  python3 -m pip install --upgrade pip
  python3 -m pip install -r pi_can_lab/requirements.txt

CAN 장비 드라이버 또는 Device Tree overlay 설정은 사용하는 HAT/USB-CAN 제품 설명서를
따릅니다. 이 도구는 Linux SocketCAN 채널 이름이 can0이라고 가정합니다.


3. SocketCAN 채널 설정
----------------------

bitrate는 실제 차량/벤치 설정과 반드시 같아야 합니다. 현재 프로젝트의 예상값은
B-CAN 100000 bit/s, I-CAN과 C-CAN 500000 bit/s입니다. 확정값이 아니므로 장비와
차량 문서로 다시 확인하십시오.

B-CAN Pi 예시:

  sudo ip link set can0 down
  sudo ip link set can0 type can bitrate 100000 restart-ms 100
  sudo ip link set can0 up
  ip -details -statistics link show can0

I-CAN/P-CAN/C-CAN Pi 예시:

  sudo ip link set can0 down
  sudo ip link set can0 type can bitrate 500000 restart-ms 100
  sudo ip link set can0 up
  ip -details -statistics link show can0

먼저 아래 명령으로 프레임이 들어오는지 확인할 수 있습니다.

  candump can0

수신이 전혀 없거나 error counter가 증가하면 송신하지 말고 배선, GND, bitrate부터
다시 확인하십시오.


4. 장비 없이 설치 검사
----------------------

각 Pi에서 한 번씩 실행하십시오.

  source .venv/bin/activate
  python3 pi_can_lab/self_test.py

마지막에 다음 문구가 나와야 합니다.

  [PASS] 모든 self-test 통과


5. 수신 장비 시작
-----------------

각 Pi에서 저장소 루트를 현재 디렉터리로 두고 실행합니다.

B-CAN Pi:

  python3 pi_can_lab/can_receiver.py --config pi_can_lab/receiver_b_can.yaml

I-CAN Pi:

  python3 pi_can_lab/can_receiver.py --config pi_can_lab/receiver_i_can.yaml

C-CAN Pi:

  python3 pi_can_lab/can_receiver.py --config pi_can_lab/receiver_c_can.yaml

P-CAN Pi:

  python3 pi_can_lab/can_receiver.py --config pi_can_lab/receiver_p_can.yaml

Ctrl+C로 종료합니다. 기본 설정은 모든 raw 프레임을 다음 파일에 계속 추가합니다.

  pi_can_lab/logs/b_can.jsonl
  pi_can_lab/logs/i_can.jsonl
  pi_can_lab/logs/p_can.jsonl
  pi_can_lab/logs/c_can.jsonl

화면에는 Hazard 후보 신호가 처음 관찰되거나 값이 바뀔 때만 출력됩니다. 화면에 보이지
않는 ID도 log_all: true 설정 때문에 JSONL에는 저장됩니다.

각 실행은 기존 JSONL에 append하지 않고 `b_can_1.jsonl`, `b_can_2.jsonl`처럼 다음 번호의
새 파일을 생성합니다. 정상 종료 또는 Ctrl+C 시 같은 번호의 `b_can_1.md` 요약 보고서도
자동 생성됩니다. I/P/C-CAN도 같은 규칙을 사용합니다. 여러 장비 로그는 파일 번호가 아니라
동일한 `--experiment-id`로 묶으십시오. 상세 판정 기준은 FUZZ_ANALYSIS.md를 참고하십시오.


6. 첫 번째 안전한 확인 절차
---------------------------

  1) 모든 송수신 장비의 시간을 chrony/NTP로 동기화합니다.
  2) 사용할 각 버스에서 수신기를 시작합니다.
  3) 아무 동작 없이 10초 이상 baseline을 기록합니다.
  4) 차량의 실제 Hazard 버튼을 한 번 누릅니다.
  5) 다시 눌러 끄고 5초 이상 기록합니다.
  6) 화면과 JSONL에서 아래 신호가 변했는지 확인합니다.

     0x65A BCM_01       / BCM1_Warnblink_Taster
     0x366 Blinkmodi_02 / BM_Warnblinken

0x65A는 버튼 입력 후보이고 0x366은 실제 점멸 상태 후보입니다. 둘 중 하나 또는 둘 다
관찰될 수 있습니다. B-CAN에서 보이지 않고 I-CAN에서만 보이면 제공된 DBC가 I-CAN용인
것과 일치하므로 B-CAN 송신 설정을 그대로 사용하면 안 됩니다.


7. DBC 기반 송신: 반드시 preview부터
---------------------------------------

송신기는 기본적으로 실제 송신을 하지 않습니다. 우선 B-CAN Pi의 두 번째 터미널에서
preview를 실행합니다. 수신기는 첫 번째 터미널에서 계속 실행해 둡니다.

Hazard 버튼 입력 후보 0x65A:

  python3 pi_can_lab/can_sender.py --config pi_can_lab/sender_hazard_button.yaml

Hazard 동작 상태 후보 0x366:

  python3 pi_can_lab/can_sender.py --config pi_can_lab/sender_hazard_status.yaml

두 설정 모두 먼저 현재 버스에서 같은 ID의 정상 프레임을 최대 5초 기다립니다. 받은
8바이트 원본에서 Hazard 신호 하나만 바꾸고 나머지 신호는 유지합니다. 해당 ID가 실제로
수신되지 않으면 송신기는 오류로 종료되며 임의의 0 payload를 만들지 않습니다.

preview의 ID, BASE, 변경 DATA를 확인한 뒤에만 --execute를 붙입니다.

  python3 pi_can_lab/can_sender.py --config pi_can_lab/sender_hazard_button.yaml --execute

기본 설정은 변경 프레임 1개를 보낸 뒤 100ms 후 캡처했던 원본 프레임 1개를 송신합니다.
이 복원 프레임은 버스 payload 복원 보조 기능일 뿐 ECU 내부 상태 복구를 보장하지 않습니다.


8. 상위 Mutator 기반 Hazard mutation
---------------------------------------

sender_hazard_mutation.yaml은 B-CAN에서 수신한 정상 0x366 live payload를 그대로
상위 저장소 Mutator의 seed로 사용합니다. DLC 8을 유지하는 서로 다른 mutation
256개를 생성하며 정상 seed payload는 mutation 구간에 포함하지 않습니다.

기본 campaign은 아래 순서로 자동 진행합니다.

  1) passive baseline 10초(송신 없음)
  2) 캡처한 정상 0x366 payload 60초 송신
  3) mutation corpus 60초 순환 송신
  4) 원본 payload 1회 복원 송신
  5) passive recovery 60초(송신 없음)

송신 간격은 10ms입니다. preview는 대기 없이 정상 payload 1개와 mutation corpus
1회를 표시합니다. 실행마다 64-bit seed를 새로 생성하므로 mutation 조합이
달라지며, 실제 seed는 TX manifest의 `mutation.random_seed`에 기록됩니다.

먼저 preview:

  python3 pi_can_lab/can_sender.py --config pi_can_lab/sender_hazard_mutation.yaml

작은 dry campaign 확인:

  python3 pi_can_lab/can_sender.py --config pi_can_lab/sender_hazard_mutation.yaml --count 16

I-CAN/P-CAN 수신을 10초 이상 먼저 시작한 뒤에만 실제 송신:

  python3 pi_can_lab/can_sender.py --config pi_can_lab/sender_hazard_mutation.yaml --execute

BM_Warnblinken을 먼저 ON/OFF로 patch한 결과를 seed로 쓰는 별도 회차는
seed source를 patched로 덮어씁니다.

  python3 pi_can_lab/can_sender.py --config pi_can_lab/sender_hazard_mutation.yaml \
    --mutation-seed-source patched --set BM_Warnblinken=0 --execute

manifest에는 각 payload의 XOR, 변경 byte/bit 수, 난수 seed와 send() 호출 직전 시각이
저장됩니다. 일반 Mutator는 BM_Warnblinken만이 아니라 0x366 전체 payload를 변조합니다.
Hazard signal-only ON/OFF 검증은 sender_hazard_status.yaml을 사용하십시오.
특정 회차를 재현하려면 manifest에 기록된 정수를 `--random-seed SEED`로 다시 지정하십시오.
각 구간은 `--baseline-duration`, `--normal-duration`, `--mutation-duration`,
`--recovery-duration`으로 임시 덮어쓸 수 있습니다.


9. Raw 프레임 송신
-------------------

먼저 preview:

  python3 pi_can_lab/can_sender.py --channel can0 --id 0x123 --data "00 11 22 33 44 55 66 77"

확인 후 실제 송신:

  python3 pi_can_lab/can_sender.py --channel can0 --id 0x123 --data "00 11 22 33 44 55 66 77" --execute

반복 횟수와 간격 지정:

  python3 pi_can_lab/can_sender.py --channel can0 --id 0x123 --data "00 11 22 33 44 55 66 77" --count 5 --interval-ms 100 --execute

기본 안전 제한은 count 최대 100, 반복 간격 최소 10ms입니다. CAN FD는 --fd를 명시해야
8바이트를 넘길 수 있습니다. 현재 제공된 DBC 후보는 Classic CAN 8바이트입니다.


10. 다른 케이스로 변경
-----------------------

먼저 DBC에서 메시지와 신호를 검색합니다.

  python3 pi_can_lab/dbc_lookup.py --dbc A5.dbc --search warnblink
  python3 pi_can_lab/dbc_lookup.py --dbc A5.dbc --id 0x366
  python3 pi_can_lab/dbc_lookup.py --dbc A5.dbc --message Blinkmodi_02

새 수신 케이스는 receiver_b_can.yaml을 복사한 뒤 receiver.watch 아래의 ids, messages,
signals를 바꿉니다. ID만 바꾸는 것이 아니라 그 ID에 속한 정확한 DBC message와 signal도
같이 바꿔야 합니다. raw 전체 기록은 계속 유지됩니다.

새 DBC 송신 케이스는 sender_hazard_button.yaml을 복사한 뒤 다음 항목을 바꿉니다.

  sender.dbc
  sender.id
  sender.message
  sender.set

CRC, checksum, counter, *_BZ 같은 신호가 들어 있는 메시지는 단순 신호 변경 후 ECU가
거부할 수 있습니다. 송신기는 이런 메시지를 기본적으로 거부합니다. 알고리즘을 구현했거나
의도적으로 비정상 CRC를 시험할 때만 --allow-protected를 사용하십시오.


11. Fuzzer 반응 상관분석
------------------------

세 장비의 시간이 NTP/chrony로 동기화되어 있어야 합니다. phased campaign manifest를
사용하면 분석기는 normal phase를 mutation에서 제외하고 mutation phase만 stimulus로
사용합니다. 기본으로 mutation 직전 10초를 baseline, 마지막 mutation 후 2초를
response, 그 뒤 10초를 recovery로 비교합니다.

  python3 pi_can_lab/analyze_fuzz_response.py \
    --tx pi_can_lab/logs/b_can_hazard_mutation_tx.jsonl \
    --rx i_can=pi_can_lab/logs/i_can.jsonl \
    --rx p_can=pi_can_lab/logs/p_can.jsonl \
    --dbc A5.dbc \
    --output pi_can_lab/logs/hazard_response.json

JSON 상세 결과와 같은 이름의 Markdown 보고서가 생성됩니다. `--output`을 생략하면
`fuzz_response_1.json/.md`, 다음 실행은 `_2`처럼 새 쌍을 만듭니다. novel direct match는 송신한
ID/payload가 다른 버스에서 관찰된 가장 강한 routing 근거입니다. 다른 ID의 신규 payload,
전송률 변화, recovery 여부는 반응 후보이며 인과관계를 단독으로 증명하지는 않습니다.


12. 문제 해결
-------------

"필수 패키지가 없습니다"
  source .venv/bin/activate 후 requirements.txt를 다시 설치합니다.

"DBC 파일을 찾을 수 없습니다"
  저장소 전체를 복사했고 저장소 루트에 A5.dbc가 있는지 확인합니다.

"원본 프레임을 수신하지 못했습니다"
  잘못된 버스, bitrate, ID 또는 I-CAN DBC를 B-CAN에 적용한 경우일 수 있습니다.
  candump can0과 can_receiver.py raw 로그를 먼저 확인합니다.

"Network is down"
  ip link set can0 up이 되지 않았거나 CAN 장비 드라이버 설정이 완료되지 않았습니다.

"decode_error"
  DLC가 DBC 정의와 다르거나 해당 버스/차량 버전에 맞지 않는 DBC일 수 있습니다.

여러 장비 로그의 시간을 비교하려면 NTP/chrony 상태를 확인하고, 각 실험 시작/종료 시각을
기록하십시오. analyze_fuzz_response.py는 마지막 TX session을 선택해 수신 로그와 자동으로
시간 상관분석합니다.
