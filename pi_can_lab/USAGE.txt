Raspberry Pi CAN Fuzzing Lab 사용법
===================================

이 문서의 모든 명령은 현재 디렉터리가 pi_can_lab인 상태를 기준으로 합니다.

  cd /path/to/auto-fuzz-26-1/pi_can_lab


0. 실험 구성
------------

각 CAN Bus는 Raspberry Pi와 CAN HAT이 하나씩 연결된 독립 장비입니다.

  B-CAN Raspberry Pi   Injection 수행 + TX manifest 기록
  I-CAN Raspberry Pi   전체 CAN traffic 수신 및 기록
  P-CAN Raspberry Pi   전체 CAN traffic 수신 및 기록
  분석 PC              B-CAN TX와 I/P-CAN RX 로그 사후 상관분석

송신, 수신, 분석은 서로 다른 프로세스입니다. 한 Raspberry Pi가 여러 CAN Bus를 동시에
제어하지 않습니다. 정확한 시간 상관분석을 위해 모든 장비의 시간을 chrony/NTP로
동기화해야 합니다.


1. 주요 파일
------------

  lab                         짧은 송신/수신 실행 명령
  can_sender.py               실제 송신 구현
  can_receiver.py             전체 raw CAN 수신 및 선택 신호 표시
  mutation_engine.py          pi_can_lab 독립 mutation 엔진
  analyze_fuzz_response.py    TX/RX 로그 사후 상관분석
  sender_hazard_mutation.yaml 0x366 mutation campaign 설정
  sender_hazard_button.yaml   0x65A Hazard 버튼 후보 설정
  sender_hazard_status.yaml   0x366 Hazard 상태 후보 설정
  receiver_i_can.yaml         I-CAN 수신 설정
  receiver_p_can.yaml         P-CAN 수신 설정
  receiver_b_can.yaml         B-CAN 수신 설정
  receiver_c_can.yaml         C-CAN 수신 설정
  dbc_lookup.py               DBC 메시지/신호 검색
  self_test.py                장비 없이 설치 및 DBC encode/decode 검사

`./lab tx`는 기본적으로 sender_hazard_mutation.yaml을 사용합니다. `--execute`가 없으면
실제 CAN 송신 없이 preview만 수행합니다.


2. 최초 설치: Raspberry Pi마다 한 번
------------------------------------

송신 코드와 mutation 엔진은 pi_can_lab 안에 함께 있습니다. A5.dbc는 기본 설정상
상위 디렉터리의 ../A5.dbc를 사용하므로 저장소 전체를 복사하는 방식을 권장합니다.

pi_can_lab 디렉터리에서 실행합니다.

  sudo apt update
  sudo apt install -y python3-venv can-utils
  python3 -m venv .venv
  source .venv/bin/activate
  python3 -m pip install --upgrade pip
  python3 -m pip install -r requirements.txt

`./lab` 명령은 가상환경을 자동으로 만들거나 활성화하지 않습니다. 위 설치는 장비마다
최초 한 번 필요합니다.


3. 터미널을 새로 열었을 때
--------------------------

pi_can_lab 디렉터리로 이동하고 가상환경을 활성화합니다.

  cd /path/to/auto-fuzz-26-1/pi_can_lab
  source .venv/bin/activate

그다음 `./lab` 명령을 사용합니다.

  ./lab --help


4. SocketCAN can0 설정
----------------------

bitrate는 실제 차량 또는 벤치 설정과 반드시 같아야 합니다. 아래 값은 현재 프로젝트의
예상값이며 차량 문서와 실제 수신 결과로 다시 확인해야 합니다.

B-CAN 장비 예시(100 kbit/s):

  sudo ip link set can0 down
  sudo ip link set can0 type can bitrate 100000 restart-ms 100
  sudo ip link set can0 up
  ip -details -statistics link show can0

I-CAN/P-CAN 장비 예시(500 kbit/s):

  sudo ip link set can0 down
  sudo ip link set can0 type can bitrate 500000 restart-ms 100
  sudo ip link set can0 up
  ip -details -statistics link show can0

먼저 수신 여부를 확인합니다.

  candump can0

수신이 없거나 error counter가 증가하면 송신하지 말고 CAN-H, CAN-L, GND, bitrate와
종단저항 구성을 다시 확인합니다. 기존 차량 버스에 임의로 120옴 저항을 추가하지 마십시오.

----------------------

  ./lab rx i

P-CAN 수신:

송신하지 마십시오.


7. 권장 실험 순서
-----------------

모든 Raspberry Pi에서 chrony/NTP 동기화 상태를 먼저 확인합니다. 서로 다른 장비의 로그는
같은 experiment ID를 지정해 묶는 것이 좋습니다. 아래의 hazard_001은 실험마다 새로운
이름으로 바꾸십시오.

I-CAN Raspberry Pi:

  ./lab rx i --experiment-id hazard_001

P-CAN Raspberry Pi:

  ./lab rx p --experiment-id hazard_001

두 수신기가 동작하는 것을 확인한 다음 B-CAN Raspberry Pi에서 0x366을 확인합니다.

  ip -details -statistics link show can0
  candump can0,366:7FF

candump에서 0x366이 반복 수신되는 것을 확인한 뒤 Ctrl+C로 종료합니다.

먼저 mutation preview를 실행합니다.

  ./lab tx --experiment-id hazard_001

preview는 CAN 프레임을 송신하지 않지만, mutation 기준 payload를 얻기 위해 can0에서
0x366 프레임을 수신합니다. 최대 5초 동안 3개를 받고 세 payload가 모두 같아야 다음으로
진행합니다.

preview에 표시된 ID, BASE, mutation payload와 random seed를 확인합니다. 실제 실행에서
preview와 동일한 mutation을 재현하려면 표시된 seed를 명시합니다.

  ./lab tx --experiment-id hazard_001 --random-seed SEED --execute

SEED는 preview에 표시된 정수로 바꿉니다. `--random-seed`를 생략하면 실행할 때 새로운
64-bit seed가 생성되어 preview와 다른 mutation corpus가 사용됩니다.

송신 campaign이 끝날 때까지 I-CAN/P-CAN 수신기를 계속 실행하고, recovery 종료 후
수신 장비에서 Ctrl+C를 눌러 종료합니다.


8. 기본 Mutation campaign
--------------------------

`./lab tx --execute`의 기본 동작은 다음과 같습니다.

  1) passive baseline 10초: 송신 없음
  2) normal 60초: 캡처한 정상 payload의 0x366 반복 송신
  3) mutation 60초: mutation한 0x366 corpus 반복 송신
  4) restore: 캡처한 정상 0x366 payload 1회 송신
  5) passive recovery 60초: 송신 없음

기본 mutation 설정:

  corpus 크기            256개
  payload 길이           8바이트 유지
  payload당 최대 연산    3개
  연산 선택              bit 단위 75%, byte 단위 25%
  원본 payload 포함      안 함
  송신 간격              10ms
  random seed            실행마다 자동 생성 및 manifest 기록

현재 normal과 mutation 송신은 모두 10ms 간격을 사용합니다. 따라서 normal 단계도 실제
차량의 원래 0x366 주기와 다를 수 있습니다. normal 단계 자체의 영향과 mutation 단계의
영향을 분리해서 해석해야 합니다.

각 구간의 시간은 명령에서 임시로 바꿀 수 있습니다.

  ./lab tx \
    --baseline-duration 10 \
    --normal-duration 30 \
    --mutation-duration 30 \
    --recovery-duration 30

mutation 개수만 줄인 preview:

  ./lab tx --count 16

DBC patch 결과를 mutation seed로 사용하는 별도 실험:

  ./lab tx --mutation-seed-source patched \
    --set BM_Warnblinken=0 --execute

기본 설정은 캡처한 정상 payload 자체를 mutation seed로 사용합니다. 일반 mutation은
BM_Warnblinken 신호만 바꾸는 것이 아니라 0x366 payload 전체를 변형합니다.

이상반응 연계 mutation은 같은 캠페인 안에서 실시간으로 수행하지 않습니다. B-CAN 송신 Pi와
I/P-CAN 수신 Pi가 분리되어 있으므로, 첫 캠페인의 로그를 분석한 JSON을 B-CAN 송신 Pi로
복사한 뒤 다음 캠페인에 입력합니다.

  ./lab tx --feedback logs/hazard_response.json

preview에서 guided payload와 random seed를 확인한 뒤 동일한 corpus를 실제 송신합니다.

  ./lab tx --feedback logs/hazard_response.json \
    --random-seed SEED --execute

기본적으로 전체 corpus의 최대 50%를 이상반응 유형에 맞춘 후보로 만들고, 나머지는 새로운
영역을 탐색하는 random mutation으로 유지합니다. 비율은 다음처럼 임시 변경할 수 있습니다.

  ./lab tx --feedback logs/hazard_response.json \
    --guided-ratio 0.5 --bit-operation-ratio 0.75

이상반응별 guided 전략:

  timing 변화             반응 byte 주변값과 00/01/7F/80/FE/FF 경계값 탐색
  새 message 출현         변경 bit/byte를 하나씩 되돌려 최소 trigger 탐색
  message 소실            원 mutation 재현 후 bit/byte 단위 복원 탐색
  payload/signal 변화     변경 field를 byte/bit 단위로 국소화
  cross-bus 반응          원 mutation 재현 후보를 우선 포함

10ms마다 서로 다른 mutation을 연속 송신하므로 분석 JSON의 source mutation은 반응 직전의
가장 가까운 TX를 연결한 후보입니다. 이것만으로 인과관계가 증명되지는 않습니다. 같은 seed의
반복 회차, no-op 대조군과 복원 여부를 사용해 재현성을 별도로 확인해야 합니다.


9. 다른 송신 preset
--------------------

Hazard 버튼 입력 후보 0x65A preview:

  ./lab tx button

Hazard 버튼 입력 후보 실제 송신:

  ./lab tx button --execute

Hazard 상태 후보 0x366 preview:

  ./lab tx status

Hazard 상태 후보 실제 송신:

  ./lab tx status --execute

button/status preset은 해당 ID의 정상 live payload를 먼저 수신하고 DBC 신호 하나만
변경합니다. 해당 ID가 수신되지 않으면 임의의 zero payload를 만들지 않고 중단합니다.
기본적으로 변경 프레임 1개를 보낸 뒤 100ms 후 캡처한 원본을 1회 송신합니다.


10. Raw 프레임 송신
--------------------

먼저 preview:

  ./lab tx raw --channel can0 --id 0x123 \
    --data "00 11 22 33 44 55 66 77"

확인 후 실제 송신:

  ./lab tx raw --channel can0 --id 0x123 \
    --data "00 11 22 33 44 55 66 77" --execute

반복 횟수와 간격 지정:

  ./lab tx raw --channel can0 --id 0x123 \
    --data "00 11 22 33 44 55 66 77" \
    --count 5 --interval-ms 100 --execute

Raw 송신 기본 안전 제한은 count 최대 100, 반복 간격 최소 10ms입니다. CAN FD payload는
`--fd`를 명시해야 8바이트를 넘길 수 있습니다.


11. 수신 명령과 로그
--------------------

I-CAN:

  ./lab rx i

P-CAN:

  ./lab rx p

추가 확인이 필요할 때 사용할 수 있는 B/C-CAN preset:

  ./lab rx b
  ./lab rx c

수신 시간 지정 예시:

  ./lab rx i --duration 120

기본값은 Ctrl+C를 누를 때까지 모든 raw 프레임을 기록합니다. 화면에는 watch 대상으로
설정된 Hazard 관련 ID 또는 신호의 변화만 표시되지만, `log_all: true`이므로 그 밖의
프레임도 JSONL에 저장됩니다.

각 실행은 기존 파일을 덮어쓰지 않고 다음 번호의 파일과 Markdown 보고서를 만듭니다.

  logs/i_can_1.jsonl
  logs/i_can_1.md
  logs/p_can_1.jsonl
  logs/p_can_1.md
  logs/b_can_hazard_mutation_tx_1.jsonl


12. 수집 로그 분석
------------------

각 Raspberry Pi의 JSONL을 분석 PC의 pi_can_lab/logs 디렉터리로 복사합니다. 실제 생성된
파일 번호를 확인합니다.

  ls -lt logs/*.jsonl

아래의 `_1`은 실제 실험에 해당하는 번호로 바꿉니다.

  python3 analyze_fuzz_response.py \
    --tx logs/b_can_hazard_mutation_tx_1.jsonl \
    --rx i_can=logs/i_can_1.jsonl \
    --rx p_can=logs/p_can_1.jsonl \
    --dbc ../A5.dbc \
    --output logs/hazard_response.json

phase 정보가 있는 TX manifest에서는 normal 단계가 stimulus에서 제외되고 mutation 단계만
분석 대상이 됩니다. 기본 비교 구간은 mutation 직전 baseline 10초, 마지막 mutation 이후
response 2초, 그 뒤 recovery 10초입니다.

JSON 결과와 같은 이름의 Markdown 보고서가 생성됩니다. 송신한 ID/payload가 다른 버스에서
직접 관찰된 경우가 가장 강한 routing 근거입니다. 다른 ID의 신규 payload, 전송률 변화,
주기 변화와 recovery 여부는 이상반응 후보이지만 단독으로 인과관계를 증명하지는 않습니다.
JSON의 `mutation_anomaly_mappings`에는 이상반응 유형, 가장 가까운 선행 mutation sequence,
payload, mutation 연산과 반응 지연이 기록됩니다. 이 파일을 다음 B-CAN 송신 회차의
`./lab tx --feedback ...` 입력으로 사용합니다.


13. DBC 검색
------------

A5.dbc는 pi_can_lab의 상위 디렉터리에 있습니다.

  python3 dbc_lookup.py --dbc ../A5.dbc --search warnblink
  python3 dbc_lookup.py --dbc ../A5.dbc --id 0x366
  python3 dbc_lookup.py --dbc ../A5.dbc --message Blinkmodi_02

현재 A5.dbc는 파일 내부 정보상 MLBevo I-CAN K-Matrix입니다. 다른 물리 CAN Bus에서 같은
ID가 실제로 존재하는지는 반드시 raw capture로 확인해야 합니다. A5.dbc 자체가 B/P-CAN의
전체 메시지를 정확하게 정의한다고 가정하면 안 됩니다.


14. 문제 해결
-------------

"./lab: Permission denied"
  chmod +x lab
  또는 python3 lab rx i처럼 실행합니다.

"필수 패키지가 없습니다"
  source .venv/bin/activate
  python3 -m pip install -r requirements.txt

"DBC 파일을 찾을 수 없습니다"
  저장소 전체를 복사했고 상위 디렉터리에 A5.dbc가 있는지 확인합니다.

"0x366 원본 프레임을 수신하지 못했습니다"
  candump can0,366:7FF로 실제 수신 여부를 확인합니다. 잘못된 물리 버스, bitrate, 배선 또는
  해당 차량 variant에서 0x366을 사용하지 않는 경우일 수 있습니다.

"baseline이 불안정합니다"
  수집한 0x366 payload 3개가 동일하지 않습니다. 다른 송신기를 중지하고 정상 차량 상태가
  안정된 뒤 다시 실행합니다.

"Network is down"
  can0가 UP 상태인지, CAN 장비 드라이버와 Device Tree overlay가 준비됐는지 확인합니다.

"decode_error"
  DLC가 DBC 정의와 다르거나 현재 물리 버스/차량 버전에 맞지 않는 DBC일 수 있습니다.


15. 안전 및 해석상 주의사항
---------------------------

- 허가된 시험 차량 또는 격리된 벤치에서만 송신합니다.
- 실제 주행 중에는 송신하지 않습니다.
- 전류 제한 전원과 즉시 차단 수단을 준비합니다.
- 송신 전에 수신기, 배선, GND, bitrate와 CAN error counter를 확인합니다.
- P/I-CAN 수신기는 B-CAN campaign 시작 전부터 recovery 종료 후까지 계속 실행합니다.
- 각 장비의 시각과 experiment ID가 맞지 않으면 TX/RX 인과성 분석 결과를 신뢰할 수 없습니다.


15. Trial 기반 3-Pi 자동 실행
-----------------------------

이전 Trial의 완료된 결과만 다음 Trial에 반영하고 SSH/SFTP로 세 Pi 로그를 자동 회수하려면
`experiment_runner.py`를 사용합니다. 상세 설정은 `TRIAL_FEEDBACK.md`를 참고합니다.

  cp experiment_runner.yaml.example experiment_runner.yaml

`experiment_runner.yaml`에 P/B/I-CAN Pi의 SSH 주소, 사용자, project_dir와 key를 입력합니다.
먼저 안전 preview로 설정 파일만 확인합니다. 이 단계에서는 SSH/CAN에 접근하지 않습니다.

  python3 experiment_runner.py \
    --target-id 0x366 --source-bus B_CAN --trials 20

격리된 벤치에서 실제 실행:

  python3 experiment_runner.py \
    --target-id 0x366 --source-bus B_CAN --trials 20 \
    --random-seed 366 --execute

각 Trial은 단일 mutation을 중심으로 baseline, normal, mutation, post 구간을 수행합니다.
세 RX와 TX 로그 다운로드가 완료된 다음에만 anomalies/feedback/state를 저장하고 다음 Trial을
